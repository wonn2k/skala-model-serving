# ③ 운영 설계

②의 운영 목표를 "어떻게 지킬 것인가"다. 기준값은 코드의 상수와 같다 (`CLAUDE.md` 상수 표). 상수를 바꾸면 이 문서도 같이 바꾼다.

## 1. 배포 게이트

새 모델은 두 관문을 모두 통과해야 서비스에 올라간다.

| 관문 | 기준 | 통과하지 못하면 | 코드 |
|---|---|---|---|
| 입력 스키마 | `/predict` 입력은 정확히 20일, 도착·출발 여객은 0 이상의 정수 | 422 Unprocessable Entity로 거부. 모델까지 가지 않는다 | `serving_app/schemas.py` |
| 성능 회귀 | 학습 데이터의 마지막 20%로 검증한 RMSE ≤ **2,700명** | 등록만 되고 Production으로 승격되지 않는다. 기존 Production 유지 | `serving_app/train_and_register.py`, `RMSE_GATE` |

**2,700명의 근거**: 일평균 37,218명의 약 7%이고, "어제와 같다"는 단순 예측(RMSE 3,600명)보다 25% 좋아야 하는 값이다 (`data/README.md`). 카운터 1개 운영 단위 수준의 오차 허용이다 (`docs/PROJECT_PLAN.md` 2번).

**측정 결과**: Day1 baseline 2,571명, Day2 MLflow 학습 2,267명으로 통과했다 (`docs/code_current.md` 2번). Day1은 여유가 129명뿐이라 PC에 따라 실패할 수 있다. 실패는 정상 동작이다. 그 PC의 RMSE를 기록하고 기존 Production을 쓴다.

## 2. 모니터링

| 항목 | 값 | 근거 |
|---|---|---|
| 지표 | 최근 예측·실제 쌍의 RMSE | 실제값이 다음 날 바로 들어오는 서비스라 예측 오차를 직접 볼 수 있다 |
| 판정 윈도우 | 최근 **21건** (`WINDOW_SIZE`) | 최근 3주. 짧으면 하루 이상값에 흔들리고, 길면 드리프트 반응이 늦다 (`serving_app/monitoring/drift_detector.py`) |
| 임계값 | RMSE > **2,700명** (`RMSE_THRESHOLD`) | 게이트와 같은 값. "게이트를 못 넘는 수준의 오차 = 드리프트"로 해석 |
| 기록 | `logs/aiops.log`에 `[WARN]` → `[INFO]` → `[OK]`, 대시보드 재학습 로그 패널 | `serving_app/main.py`, `routers/logs.py` |

윈도우와 임계값을 바꾸면 오탐과 미탐이 이렇게 달라진다.

- 윈도우를 짧게 잡으면 결항 하루에도 판정이 나고(오탐 증가), 길게 잡으면 수요 패턴이 바뀐 뒤 3주 넘게 모른다(미탐 증가).
- 임계값을 낮추면 평상시 변동에도 재학습이 돌고, 높이면 실제 드리프트를 놓친다.

## 3. 드리프트 대응 정책

```
오차 > 임계값 → [WARN] 알림 → 최근 21일 + 시퀀스용 20일로 fine-tuning → 게이트 재검증
   → 통과: Production 재배포 ([OK])
   → 실패: 기존 Production 유지
```

- **왜 처음부터 다시 학습하지 않는가**: 최근 41일로 만들 수 있는 학습 시퀀스는 21개뿐이라 스크래치 학습은 불안정하다. 전체 기간으로 학습된 Production 가중치에서 낮은 학습률(1e-4)로 10 epoch만 이어서 학습한다 (`serving_app/train_and_register.py`의 `fine_tune`).
- **재학습도 게이트를 거친다**: 재학습된 모델이 더 나쁘면 올라가지 않는다. 운영 담당자는 "재학습이 돌았다"는 사실이 아니라 "지금 서비스 중인 모델은 게이트를 통과한 모델"이라는 사실을 믿으면 된다.
- 데이터는 대시보드에 마지막으로 업로드된 파일의 최근 41행을 쓴다 (`data/storage.py`).

## 4. 확정 전 이슈와 팀 결정 사항

사전 실험(2026-10-01, 임시 복사본, PC 1대, 1회 측정. 상세는 팀 노션 "실험 결과")에서 다음이 관찰됐다. 상수 변경은 팀 합의 후 PR 하나로 한다.

| 이슈 | 관찰 | 선택지 |
|---|---|---|
| **임계값이 평상시 오차와 거의 같다** | 결항일을 뺀 평상시 하루 오차가 모델 2,275~2,570명, 전일값 복사 2,502명. 학습에 쓰이지 않은 평상시 구간에서 41일 배치의 32%(출발 여객 고정) / 13%(실제 출발 여객)가 임계값을 넘음 | 드리프트 임계값을 게이트와 분리해 올린다. 평상시 최대(4,122명 고정 / 3,464명 실제 출발)와 폭설 배치(5,944~6,524명) 사이에 두면 둘이 갈린다 |
| **배치 판정 시 출발 여객을 37,000으로 고정** | 같은 배치가 고정값으로 3,715명, 실제 출발 여객으로 2,754명. 고정값이 250~950명의 오차를 더함 | `/predict/batch-test`에 `departures`를 선택 항목으로 받는다 (스키마·명세·대시보드 함께 변경) |
| **재학습이 오차를 줄이지 못함** | 변동이 큰 기간(2025년 10월)은 재학습 전 3,142명, 후 3,238명. 전일값 복사도 3,125명 | 재학습으로 해결되는 드리프트(수준 변화)와 안 되는 변동(연휴·결항)을 구분해서 설명 |
| 재학습 검증 표본이 5일뿐 | fine-tuning RMSE는 최근 41행 중 마지막 5일로만 검증되어 우연에 좌우됨 (수업 가이드 부록 2) | 검증셋 확보 방안을 확장 계획으로 |
| 재배포 후 서빙 모델이 안 바뀜 | `_model_cache`가 재학습 후 갱신되지 않음 (수업 가이드 부록 1의 6번) | 승격 시 캐시를 비우도록 보완 (서빙 담당) |
| 재학습 직후 다시 드리프트 판정 | 판정 윈도우에 재학습 전 예측이 남아 있음 (부록 1의 7번) | 재학습 후 윈도우 초기화 정책 결정 |
| 시뮬레이션 변동성이 실제보다 낮음 | 스크립트 σ 1.2% / 3.6%, 실데이터 8.4% (`data/README.md`) | 시연은 실데이터 배치를 쓴다 |
